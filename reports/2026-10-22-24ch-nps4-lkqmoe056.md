# 2026-10-22：lkqmoe 0.5.6 + 24 通道内存、NPS4（Qwen3.8 Flash Next）

## 变化

- 内存补满到 24 × 16 GiB DDR5-4800（384 GiB），BIOS 改 NPS4（8 个 NUMA 节点）。
- `lkqmoe/` 换成 0.5.6 编译版，与 lsglang_ds4.1 是同一份（AVX512 库 `-DLKQMOE_DOWN_R4=1`）；`python/sitecustomize.py` 支持 `LKQMOE_MAIN_CPUS=auto`。
- 新增 `launch/run-qwen38fn-nvfp4-24ch-nps4.sh`：主线程用 `LKQMOE_MAIN_CPUS=auto`（允许的 CPU − 专家线程 − 信箱调度线程，NPS4 下 15 个逻辑 CPU，与专家线程零重叠）。
  原脚本里按 NPS2 写的列表在 NPS4 下会与 lkqmoe ≥ 0.5.2 的专家线程重叠，所以保留给 20 通道 / NPS2 用。

- 并发：1 个请求 154.1 → 145.9 tok/s；2 个请求合计 217.0 → 202.2 tok/s（每个 109.5）。
- 困惑度 3.4817 → 3.4779，各长度都找回埋藏事实；显存峰值与之前相同。
- Qwen 的 23 个池层里 82–90% 的专家由 GPU 承担，decode 主要受 GPU 限制，所以 NPS4 与 CPU 提速对它帮助很小；按每步耗时（接受长度 ÷ decode）单请求与并发都与 10-14 持平，tok/s 的差别来自接受长度的波动。112 线程比 64 线程每次 CPU 调用快约 19%（单层快 17–23%），整机持平，双并发时 CPU 工作更多，所以默认 112。
- 首 token 各长度与之前一致：长预填充受 GPU 计算和 PCIe 上传限制，不受内存通道影响。

## GPU 与 CPU 谁在等谁（WebUI 正式启动后，只开 GPU 的 40 步剖析）

- 23 个池层每步各一次 CPU 专家调用；GPU 热池内核每次平均 68 µs，GPU 等 CPU 平均只有 9 µs（95% 的调用在 5–20 µs，
  约等于信箱通知本身的延迟），CPU 与 GPU 基本同时完成；每步热池 1.6 ms、等 CPU 0.2 ms。
- 一步约 15 ms 里大头在 GPU 的其他部分：BF16 GEMM（含词表头）、常驻层 Marlin W4A16 MoE（约 2.2 ms）、hc_mix（约 1.7 ms）等；
  CPU 每步只忙约 1.5 ms。
